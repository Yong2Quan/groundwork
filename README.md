# Groundwork: incident triage, three ways, with an eval harness

An incident-triage system built three times over the same data - a model on
its own, retrieval over runbooks, and an agent looping over MCP tools - and a
harness that scores all three on root-cause accuracy, tool calls, latency and
cost.

The question it exists to answer is not "can an LLM do triage". It is **when
retrieval is enough and when you actually need an agent**, which is a
question you can only answer with a number.

> **The data is synthetic.** Thirty incidents, ten runbooks and all metric
> series are generated by [`scripts/generate_data.py`](scripts/generate_data.py).
> No client data, no real system names, no real incidents. The results below
> therefore demonstrate a *method*, not real-world triage performance. The
> absolute accuracy numbers mean nothing outside this corpus; the gaps
> between configurations on the same corpus are the finding.

---

## The idea that makes the comparison mean something

Measuring three configurations against one undifferentiated accuracy number
tells you which one won. It does not tell you *when* to use which, which is
the only thing a team actually needs to decide.

So every incident is labelled with an **answerability tier** - what a
responder must read in order to get it right:

| Tier | n | What it takes |
| --- | ---: | --- |
| `ticket_sufficient` | 8 | The ticket names the signature outright (`exit code 137`, `ENOSPC`). |
| `runbook_sufficient` | 11 | The symptom is in the ticket; the symptom-to-cause mapping is in a runbook. |
| `evidence_required` | 11 | The ticket is deliberately ambiguous across two or three causes. Only the metric series or past incidents decide. |

The tiers are the independent variable. An agent should buy you nothing on
tier 1, little on tier 2, and everything on tier 3 - and if it doesn't, it
isn't earning its latency and cost.

Tier 3 is constructed, not asserted. Six incidents share one generic "p99 is
up and customers are timing out" complaint, and the true cause is separated
only by metrics:

| Evidence | Root cause |
| --- | --- |
| `db_active_connections` pinned flat at the pool max, `db_query_time_p99` normal | `connection_pool_exhaustion` |
| `db_query_time_p99` climbing, connections well below max | `db_slow_query_missing_index` |
| `upstream_5xx_rate` rising *before* our own latency, database flat | `upstream_dependency_outage` |

`triage analyze` verifies that these tickets genuinely do not give their own
answers away - see [Validity checks](#validity-checks).

## Results

Claude Sonnet 5.5 (`--model sonnet`) via the Claude Code CLI, 90 runs (3 configurations x 30
incidents), 14 minutes of model time, $2.51 list-equivalent. Raw run:
[`results/runs/sweep-sonnet.json`](results/runs/sweep-sonnet.json) -
re-render with `triage report`.

| Configuration | Accuracy | Abstained | Confidently wrong | Tool calls | Median latency | Cost / incident |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Rules only, no LLM *(control)* | 63% (19/30) | 0% | **11** | 0.0 | <0.01s | $0.0000 |
| LLM alone | 60% (18/30) | 40% | **0** | 0.0 | 3.5s | $0.0087 |
| RAG over runbooks | 63% (19/30) | 37% | **0** | 0.0 | 4.1s | $0.0130 |
| Agent over MCP tools | **100%** (30/30) | 0% | **0** | 1.6 | 18.6s | $0.0618 |

### Accuracy by answerability tier

| Configuration | Ticket is enough | Needs a runbook | Needs evidence |
| --- | ---: | ---: | ---: |
| Rules only, no LLM *(control)* | 88% (7/8) | 73% (8/11) | 36% (4/11) |
| LLM alone | 100% (8/8) | 82% (9/11) | 9% (1/11) |
| RAG over runbooks | 100% (8/8) | 91% (10/11) | 9% (1/11) |
| Agent over MCP tools | 100% (8/8) | 100% (11/11) | **100% (11/11)** |

The control arm is BM25 term-matching with no language model at all
([`results/runs/control-rules.json`](results/runs/control-rules.json), run
with `triage run --provider offline`). Read its first row against RAG's:
**identical accuracy, 63% each.** On the hardest tier it appears to *beat*
both LLM arms, 36% against 9%.

It is also the worst system in this table, by a long way. It reaches that
63% by never abstaining - guessing on all 30 - and it is confidently wrong
**11 times**. Its apparent 36% on `evidence_required` is a keyword matcher
picking between two or three candidates it cannot distinguish, which is
roughly what chance looks like there.

That is the whole argument against accuracy as a headline metric, in one
row. Two systems, same score, one safe to deploy and one not.

### Which tools the agent actually used

| Tool | Calls | Share |
| --- | ---: | ---: |
| `get_metrics` | 34 | 71% |
| `get_ticket` | 12 | 25% |
| `search_runbooks` | 2 | 4% |

## Does the architecture win, or does the model?

One model cannot answer that. The whole sweep was repeated on Claude Haiku
5.5 - a far cheaper model - to separate "agents beat RAG" from "Sonnet 5.5
beats RAG". Reproduce with
`triage compare results/runs/sweep-sonnet.json results/runs/sweep-haiku.json`.

| Configuration | Sonnet 5.5 | Haiku 5.5 |
| --- | ---: | ---: |
| LLM alone | 60% (18/30) | 53% (16/30) |
| RAG over runbooks | 63% (19/30) | 53% (16/30) |
| Agent over MCP tools | 100% (30/30) | **93% (28/30)** |

On the tier that the whole experiment is built around:

| Configuration | Sonnet 5.5 | Haiku 5.5 |
| --- | ---: | ---: |
| LLM alone | 9% (1/11) | 9% (1/11) |
| RAG over runbooks | 9% (1/11) | 9% (1/11) |
| Agent over MCP tools | **100% (11/11)** | **100% (11/11)** |

**The architecture effect is model-independent; the model effect is not.**
Dropping from Sonnet to Haiku costs 7 points on the headline. Removing tool
access costs 40. On `evidence_required` the two models are identical at
every configuration - including a perfect 11/11 for both agents. Whatever
the agent is doing there, it is not something only a frontier model can do.

### The comparison that should change how you build

| | Accuracy | Cost / incident |
| --- | ---: | ---: |
| **Haiku 5.5 agent** | **93%** | **$0.0047** |
| Sonnet 5.5 RAG | 63% | $0.0130 |

The cheap model with tools beats the expensive model without them on
accuracy by 30 points *and* costs 2.8x less. If you are choosing between
"upgrade the model" and "give it access to the data", on this corpus the
second is both better and cheaper, and it is not close.

### Haiku also de-saturated the benchmark

Sonnet's agent scored 100%, which left the corpus unable to rank anything.
Haiku's 93% restores some discrimination - and the two misses are more
interesting than the number.

## Failure analysis

### Nothing was ever confidently wrong. The difference is resolution, not correctness.

The headline accuracy column is the least interesting one here. Across all
90 runs, **no configuration produced a single confident wrong answer**. The
non-agent arms did not hallucinate root causes; they abstained - 12 times
for the LLM alone, 11 for RAG - and they abstained on almost exactly the
incidents they had no way to solve.

That reframes the result. "60% vs 100%" is not "wrong 40% of the time
versus never". It is **"reaches an answer 60% of the time versus always"**,
with the shortfall landing in honest `unknown`s. A RAG system that abstains
is safe to put in front of a human; one that guesses is not. This only
shows up because the answer set includes an explicit `unknown` option and
the harness reports abstention separately from error - without that, these
three rows would look far more alarming than they are.

**The abstentions were precisely targeted, which is what makes routing
work.** RAG abstained 11 times: on 10 of the 11 `evidence_required`
incidents, plus `INC-016` - the one incident whose tier label is wrong and
which is really evidence-required too. **Zero false abstentions.** It never
gave up on an incident it could actually have solved.

So `unknown` is not noise, it is a near-perfect detector for "this one
needs live evidence". You do not have to predict which incidents need an
agent; the cheap arm tells you. That is the entire basis of the routing
design costed in [What it costs to run](#what-it-costs-to-run), and it is
worth re-verifying on any new corpus before relying on it.

### RAG bought one incident. The runbooks were nearly worthless.

RAG beat the model alone by a single incident (19 vs 18), despite retrieving
the correct runbook 91% of the time on the tier it was built for. Retrieval
was not the bottleneck - the model already knew the operational lore. It
does not need a document to tell it that exit code 137 means OOM.

The agent corroborates this from the other direction: across 30 incidents it
called `search_runbooks` **twice**. 71% of its tool calls were
`get_metrics`. It did not want the *procedure*, it wanted the *data*.

That is the finding with the most transfer to real work. A runbook corpus
that encodes what a competent engineer already knows adds cost and latency
and almost no accuracy. The retrieval target has to be something the model
genuinely does not know - internal conventions, your specific topology,
decisions your team made - not general practice.

### The 100% is benchmark saturation, not a perfect agent.

The agent solved every incident, which means **this corpus can no longer
tell a good agent from a great one**. The ceiling has been hit and the
remaining headroom is zero. Any future change - a cheaper model, fewer
tools, a worse prompt - would have to be measured against a harder corpus
to show up at all.

It also suggests the evidence is too clean. Each incident has exactly one
metric window, twenty series, and an unambiguous signature. Real triage
involves several plausible windows, missing data, and series that moved for
unrelated reasons. A v2 should add distractor windows and unrelated
concurrent anomalies.

### The model found a labelling error I made.

`INC-016` was labelled `runbook_sufficient`. Both non-agent arms abstained on
it, and the RAG arm's reasoning explains why - having retrieved the correct
TLS runbook at rank 1:

> "That rules out connection pool exhaustion, disk full, memory leak, queue
> lag and stampede, which all ramp or show resource pressure. It does not
> separate an expired TLS certificate from a bad deploy, config drift or a
> DNS failure, because each of those [is also a step function]."

That is correct, and my tier label was wrong. RB-002 itself says the metric
shape is the giveaway, so the incident is `evidence_required` - the runbook
tells you to go and look at `tls_handshake_failures`, which RAG cannot do.
The agent got it right by calling `get_metrics` and observing
`tls_handshake_failures` rise from 0 to 808.7, exactly equal to the request
rate.

**The label has deliberately not been corrected.** Re-tiering an incident
after seeing which configuration it favours is precisely the data-fitting
this project is supposed to avoid. It is recorded here instead, and it means
the true `runbook_sufficient` count is 10, not 11.

### What the one shared success tells us

`INC-030` is the only `evidence_required` incident the non-agent arms got
right, and both got it. Its ticket says the team "reduced our write rate as
a precaution but it has not obviously helped" - which is the documented
difference between a quota and a rate limit. A mild tell survived the
leakage check, because the check tests term overlap and this is a semantic
hint. Worth fixing in a v2, and worth noting as a limit of automated
leakage checking: it catches lexical giveaways, not inferential ones.


### Haiku's two misses: over-abstention, not error

Both failures are `queue_consumer_lag` (`INC-005`, `INC-017`), both are
abstentions, and neither is a reasoning failure. Haiku found the right
evidence and then declined to name it. From its `INC-017` verdict:

> "queue_depth went from a baseline of about 1.4k to an incident average of
> about 126k... consumer_lag_seconds went from about 8s to about 1.8k s...
> Write volume is flat (request_rate 809 to 822), so consumers are not
> keeping up with unchanged input. **That fits queue_consumer_lag as a
> description of the symptom, but the question is what reduced consumer
> capacity, and the evidence does not isolate that.**"

It then ruled out all thirteen other causes individually, with numbers, and
answered `unknown` at confidence 0.35.

This is a **task-specification failure, not a capability failure**. Haiku
treated "root cause" as requiring a deeper causal level than the taxonomy
contains - it wanted to know *why* the consumers slowed, not merely *that*
they had. Arguably it is being more rigorous than the task deserves. The
fix is prompt and taxonomy work, not a bigger model: say explicitly what
depth of cause counts as an answer.

It matters for how you read the headline. Haiku's agent is not 93%
*accurate and 7% wrong*; it is 93% resolved and 7% escalated, with zero
wrong answers - the same safe-failure profile as every other arm here.

### Haiku found a defect in the corpus that I missed

Buried in that same verdict:

> "restart_count reads 0 across the window, which contradicts the reported
> crash-looping"

It is right. `INC-017`'s ticket says "two of the six indexer replicas have
been crash-looping", but the `queue_consumer_lag` metric profile never
touches `restart_count`, so it is flat at zero for the entire window. The
ticket and the metrics contradict each other, and that contradiction is
part of why Haiku would not commit.

Neither I nor Sonnet caught this. A weaker model reading the numbers more
literally did.

**Not fixed, for the same reason `INC-016` was not re-labelled.** Repairing
the corpus after seeing that the defect cost one arm a point would improve
Haiku's score, which is exactly the direction that makes a post-hoc fix
illegitimate. It is logged here and belongs in a v2, along with a
generator-level check that every claim in a ticket is reflected in at least
one series.

### And it hallucinated a missing tool

The same verdict ends:

> "the find_similar_incidents tool was not available to me, so I could not
> check precedent"

This is false. The tool was in the catalogue, and Haiku called it
successfully twice elsewhere in the same sweep. It invented a missing
capability to justify abstaining.

Worth naming because it is a failure mode that survives every guardrail in
this project: the output was schema-valid, the confidence was appropriately
low, the answer was a safe `unknown`, and the reasoning was detailed and
mostly correct. Nothing in the harness flags it. Only reading the trace
against the tool log catches it - which is an argument for recording the
trace, and for not trusting a model's account of its own tool access.

## What it costs to run

Accuracy is the wrong headline for triage. An operations team cares about
how many incidents get resolved without a human, how many get escalated,
and how many send someone to fix the wrong thing - and those have very
different costs.

`triage economics` prices the outcomes. Inputs are in **engineer-minutes**
rather than currency, because nobody knows their fully-loaded hourly cost
offhand but anyone who has run an on-call rota can estimate how long a
human takes to triage from scratch. Defaults: 20 minutes for an escalation,
45 for a misdirection, $75/hr.

| Deployment | Resolved / 100 | Escalated | Misdirected | Model cost | **Total / 100** |
| --- | ---: | ---: | ---: | ---: | ---: |
| LLM alone, escalate abstentions to the agent | 100 | 0 | 0 | $3.80 | **$3.80** |
| RAG, escalate abstentions to the agent | 100 | 0 | 0 | $4.07 | **$4.07** |
| Agent on everything | 100 | 0 | 0 | $6.18 | $6.18 |
| RAG alone | 63 | 37 | 0 | $1.30 | $917.96 |
| LLM alone | 60 | 40 | 0 | $0.87 | $1000.87 |
| Rules only, no LLM *(control)* | 63 | 0 | **37** | $0.00 | **$2062.50** |

**The control arm is free to run and, at the default 45-minute
misdirection cost, still the most expensive option here.** Zero model cost,
zero latency, the same 63% accuracy as RAG - and
$2,062 per 100 incidents, because it never abstains and sends an engineer
the wrong way 37 times. Reproduce with
`triage economics results/runs/control-rules.json`.

That ranking does rest on one assumption, so it is worth stating. The
control misdirects 11 incidents; RAG escalates 11. The two cost the same
when a misdirection costs the same as an escalation, so **the control is
worse than RAG only if a misdirection costs more than ~20 engineer-minutes**
- below that it is cheaper (at 5 minutes, $229 per 100). The assumption is
defensible, because a misdirection *is* an escalation plus the time spent
acting on the wrong answer first, so it should cost strictly more. But it
is an assumption, and `triage economics` now sweeps it rather than fixing
it. What survives every setting is the comparison against the agent: the
control is more expensive at all of them.

Two more things fall out of this.

**Routing on abstention is cheaper than running the agent on everything,
at identical accuracy: 39% for `LLM alone -> agent`, 34% for
`RAG -> agent`.** The cheap arm answers what it can and
says `unknown` otherwise; only those incidents reach the agent. This holds
at *every* escalation cost tested (5 to 90 minutes), because both routes
resolve 100% and therefore never pay the escalation term at all. It is the
one conclusion here that does not rest on an assumption you would have to
defend.

**RAG does not earn its place even as a pre-filter.** `LLM alone -> agent`
beats `RAG -> agent`: RAG costs 50% more per incident and resolves exactly
**one** more of thirty on its own (19 vs 18 - the 3-point gap is
percentage points, not incidents), so it hands off nearly as much work
while charging more to do it.

The catch, stated plainly: routing on abstention is only safe because no
configuration here was ever confidently wrong. If the cheap arm guesses,
its wrong answers are never escalated and never caught - the cost lands
directly in the misdirection column, which is the most expensive one.
`tests/test_economics.py` pins that behaviour.

## Architecture

```
                    ┌─────────────────────────────┐
   incident ───────▶│  (a) baseline               │──▶ verdict
                    │      ticket only            │
                    ├─────────────────────────────┤
   incident ───────▶│  (b) rag                    │──▶ verdict
                    │      + BM25 runbook chunks  │
                    ├─────────────────────────────┤
                    │  (c) agent                  │
   incident ───────▶│      ReAct loop ◀──┐        │──▶ verdict
                    └────────────────────┼────────┘
                                         │ stdio (MCP)
                              ┌──────────▼───────────┐
                              │  triage MCP server   │
                              │  search_runbooks     │
                              │  get_ticket          │
                              │  get_metrics         │
                              │  find_similar_incidents │
                              └──────────────────────┘
```

All three arms share one system prompt, one closed answer set of 14 root
causes, and one JSON output contract. The *only* difference between them is a
single clause describing what they can reach. That is enforced by a test
(`test_the_three_arms_share_everything_but_the_access_clause`) - otherwise
the experiment would be comparing prompt engineering, not architectures.

Scoring is exact match of `root_cause_id` against the known label. No LLM
judge: with a closed list of 14 causes, string equality settles it, and a
judge would only add cost, latency and a second source of error.

### The agent loop lives in the harness, not the model runner

The original design let Claude Code attach the MCP server and drive tool use
itself. A remote organization policy on this machine blocks that
(`MCP server blocked by enterprise policy`). Rather than work around a
security control, the harness owns the MCP client: it connects with the
official Python SDK over stdio, lists the tools, and runs the loop, using the
provider purely as a completion endpoint.

This turned out better than the original plan. The loop is provider-agnostic,
and every step is recorded, which is what makes the failure analysis
possible. The tradeoff is honest and reported: the transcript is re-sent each
step, so the agent arm pays for its own history where native tool calling
would amortise it through prompt caching. Agent cost here is an upper bound.

### Tool design decisions

- `get_metrics` returns per-series summaries, not 36 raw samples across 20
  series. The full dump is ~15k tokens of mostly-baseline noise per call.
  Raw values are available for named series on request.
- `get_metrics` **refuses an ambiguous window** rather than picking one.
  `checkout-api` has five retained windows; guessing would hand the agent
  another outage's metrics and the eval would score reasoning done over the
  wrong evidence. This was a real bug - see [BUILD_LOG.md](BUILD_LOG.md).
- No tool ranks or flags anomalies. A tool that returned "the series that
  moved most" would be doing the diagnosis.
- `find_similar_incidents` deliberately returns neighbours with *differing*
  root causes. If similarity search answered every question, the agent would
  look good for a reason that would not survive a real incident database.
- No tool can reach the ground-truth label. There is a test that walks all 30
  incidents and asserts no tool response ever contains it.

## Running it

```bash
uv venv && uv pip install -e ".[mcp,dev]"
python scripts/generate_data.py      # regenerate the corpus (deterministic)
pytest                               # 71 tests, no model, no network
```

### Free analysis, no model

```bash
triage analyze                       # corpus, retrieval quality, validity checks
triage run --provider offline        # rules-only control arm, instant, $0
```

### The sweep

```bash
triage run                           # all 3 arms x 30 incidents
triage run --limit 3                 # smoke test first
triage run --resume --out results/runs/sweep.json
triage report                        # re-render tables from the latest run
```

**Model access.** The default provider is `claude_cli`, which shells out to
an installed Claude Code CLI in headless mode. It needs **no API key** - it
runs on an existing Claude Code subscription. The default model is
`sonnet`; pass `--model opus` for the stronger arm.

With an API key instead, use `--provider anthropic` (reads
`ANTHROPIC_API_KEY`, or `TRIAGE_BEDROCK_REGION` for Bedrock). That path is
implemented but, lacking credentials here, has not been exercised - treat it
as untested.

**About the cost column.** Under `claude_cli` the figure is Claude Code's own
estimate at *list API prices*. On a subscription you are not billed it. It is
the right number for comparing arms against each other and the wrong number
to quote as running cost. It also includes Claude Code's harness overhead
(~900-4000 cached tokens per call), which applies equally to all three arms.

### Inspecting the MCP server by hand

```bash
triage serve                         # stdio
triage inspect                       # prints the MCP Inspector command
```

The Inspector gives you a browser UI to call each tool, read its schema and
check responses without any model in the loop.

## Validity checks

`triage analyze` runs these before you spend anything. If the leakage check
fails, the eval is invalid and no amount of model spend will fix it.

- **Retrieval quality.** Recall@3 of the gold runbook, per tier. RAG has to
  be a competent baseline or the comparison is worthless; currently 91% on
  `runbook_sufficient`, so when RAG gets one of those wrong it is a reasoning
  failure, not a retrieval failure.
- **Answer leakage.** For every `evidence_required` incident, checks that
  term overlap cannot single out the true cause from its designated
  distractors. Deliberately strict about its own method: it requires two
  measures with opposite corpus-size biases to agree, because each one alone
  produced false leak reports during construction.
- **No label leakage through tools.** All 30 incidents, every tool, asserts
  the answer never appears in a response.
- **Prompt parity.** The three arms differ by exactly one clause.

## Deviations from the original brief

Four, each deliberate:

**Synthetic data is generated deterministically, not drafted by an LLM.** The
brief called for LLM-drafted incidents checked by hand. A seeded generator
was chosen instead because the labels *are* the experiment: for the
`evidence_required` tier, the metric profile and the root-cause label have to
agree exactly, or the incident is unanswerable by anyone and the tier
silently becomes noise. A generator makes that relationship auditable by
reading one file, and makes the corpus byte-reproducible. The cost is that
the ticket prose is less varied than an LLM would write; `tests/test_dataset.py`
pins the profile-to-label agreement that this buys.

**The agent loop lives in the harness rather than in the model runner.** Not
a preference - a remote organization policy blocks MCP servers in Claude
Code on this machine. See [Architecture](#the-agent-loop-lives-in-the-harness-not-the-model-runner).

**A fourth arm was added.** A rules-only control (BM25, no LLM) that the
brief did not ask for. It answers a question the other three cannot: how much
of the headline accuracy is the language model actually contributing, versus
how obvious the easy incidents are.

**Claude via the Claude Code CLI, not Bedrock.** The brief said "Bedrock or
anything free and available". There are no AWS credentials and no API budget
here; the Claude Code CLI runs on an existing subscription at no additional
cost. The Bedrock and direct-API paths are implemented behind
`--provider anthropic` but untested.

## Honest limitations

- **The benchmark is saturated for Sonnet.** Its agent scored 100%, so the
  corpus cannot rank anything at or above that level; those numbers are a
  floor, not a measurement. Haiku's 93% restores some discrimination, but
  the ceiling is still close. A v2 needs distractor metric windows,
  unrelated concurrent anomalies, and incidents with genuinely missing
  evidence.
- **`INC-017` contains a contradiction between its ticket and its metrics**
  (crash-looping replicas, `restart_count` flat at 0), found by Haiku and
  left unfixed on purpose - see the failure analysis. A v2 should assert at
  the generator level that every claim in a ticket appears in some series.
- **Synthetic data, single corpus.** Thirty incidents is enough to see a tier
  effect and not enough for a confidence interval worth quoting. Treat
  differences of a few points as noise - the RAG-over-baseline gain of one
  incident is firmly inside it, and should be read as "no measurable gain".
- **Two models, one run per cell.** No repeats, so per-incident variance
  is unmeasured, and two models is enough to show the architecture effect
  is not model-specific but not enough to characterise it.
  The three tier results are far apart enough to survive that; the 60%-vs-63%
  headline gap is not.
- **The tiers are my judgement, and at least one is wrong.** `INC-016` is
  labelled `runbook_sufficient` but is really `evidence_required` - see
  [the failure analysis](#the-model-found-a-labelling-error-i-made). It has
  deliberately not been corrected after the fact.
- **The leakage check catches lexical giveaways, not inferential ones.**
  `INC-030` passed it and still contains a semantic hint.
- **The agent's cost is an upper bound** for the reason given above.
- **`--provider anthropic` is untested** for lack of credentials.
